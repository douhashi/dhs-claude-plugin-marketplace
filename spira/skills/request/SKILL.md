フィードバック「$ARGUMENTS」を確認・調査し、必要な Issue を起票してください。

## Philosophy

- **事実で受け止める**: フィードバックは主張であり、事実ではない。コード・ドキュメント・Issue で裏を取ってから判断する
- **声の奥の課題を見る**: 書かれた解決策ではなく、困りごとそのものを捉える
- **起票は手段**: 既存 Issue・仕様どおりの挙動・誤解で説明がつくなら、起票しない
- **借りた言葉で話す**: 用語はコードベースとドキュメントに実在する語を使う

## Role

あなたは**フィードバックを調査し、対応要否を判断するトリアージ担当**です。

## 禁則事項

- 調査せずに起票要否を判断することは禁止
- コード・ドキュメントの書き換えは禁止（修正は起票した Issue を通して行う）
- `gh issue create` を直接実行することは禁止。起票は必ず `spira:create-issue` を通す
- 既存 Issue へのコメント・ラベル変更・クローズは禁止
- 推測を事実として報告することは禁止。確かめられなかったことは「未確認」と書く

## 入力の解析

- **`$ARGUMENTS` あり**: フィードバックの本文として扱う
- **`$ARGUMENTS` なし**: 会話の文脈からフィードバックを特定する。特定できなければ、内容を 1 文で尋ねて待つ

## 手順

### Phase 1: 最新化

`git status` で作業ツリーを確認し、クリーンなら `git switch main && git pull` で最新化する。
未コミットの変更があれば最新化せず、その旨を報告に含めて進める（stash・破棄はしない）。

### Phase 2: 内容の確認

フィードバックを**観点ごと**に分ける（1 つのフィードバックに複数の話が混ざっていることがある）。
各観点について、次を整理する。

- 何が起きている・何に困っているか（書かれた解決策とは分けて捉える）
- 種別: `不具合` / `改善要望` / `質問` / `その他`

再現条件や対象が読み取れず、調査の方向が定まらない観点があれば、**まとめて 1 回だけ**質問する（最大 3 つ）。
調査で埋められることは聞かない。

### Phase 3: 調査

観点ごとに、次を調べる。

1. **コードとドキュメント**: 該当箇所を Grep / Read で特定し、フィードバックの主張が現状と合うかを確かめる。
   不具合なら原因の箇所、要望なら現状の仕様と、それを定めたドキュメントの記述を押さえる
2. **既存 Issue**: `gh issue list --state all --search "<キーワード>" --limit 20` で重複・関連を探す。
   候補は `gh issue view <番号>` で本文を読んで判断する
3. **ロードマップ**: `find docs -name roadmap.md -type f 2>/dev/null | head -1` があれば Read し、関連する行を確かめる

調査結果から、観点ごとに対応を 1 つに決める。

| 対応 | 条件 |
|:--|:--|
| `起票` | 現状と食い違う不具合、または仕様にない改善で、既存 Issue に無い |
| `既存 Issue` | Open な Issue が同じ課題を扱っている |
| `対応済み` | 最新の `main` で解消している（クローズ済み Issue・マージ済み PR で確かめる） |
| `仕様どおり` | ドキュメントに定めた挙動で、変える理由が見つからない |
| `判断保留` | 方針が決まらず、議論（`spira:brainstorming`）が先に要る |

### Phase 4: 調査結果の提示

[templates/investigation-report.md](templates/investigation-report.md) を Read し、その雛形どおりに提示する。

`起票` が 0 件なら、ここで終了する。

### Phase 5: 起票とロードマップ更新

`起票` の観点があれば、Skill ツールで `spira:create-issue` を呼び出す。

1. `起票` の観点と、その調査結果（原因の箇所・関連 Issue・現状の仕様）を Issue 化の入力とする
2. **読み込まれた create-issue の手順を最後まで実行する**。一覧表の提示 → 承認 → 起票 → ロードマップへの追記（PR → マージ） → 報告まで自分で行う
3. Issue 本文の背景には、フィードバック由来であることと調査で確かめた事実を書く

**起票の承認は `spira:create-issue` が行う。** このスキルで Issue の一覧を先に出さない。
ユーザーが起票を見送った場合は、その旨を報告して終了する。
