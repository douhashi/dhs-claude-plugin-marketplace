# テンプレート: 作成予定 Issue 一覧

- **書き手**: create-issue スキル
- **用途**: 起票前にユーザーの承認を得る

## 起票の可否

起票できるのは、**完了したときにコードベースの状態が変わる** Issue だけ。
「何をするかを決める」ことが本体の項目は Issue にしない。

判定は完了条件で行う。完了条件をコード・ドキュメント・設定の差分として
書けるなら起票する。「〜が決まっている」「〜の方針が固まっている」としか
書けないなら起票しない。

| 判定 | 例 |
|:--|:--|
| 起票する | `feat(spira): 論点テーブルに状態列を追加する` / `docs: architecture.md に配布先の節を追加する` / `fix(tts-notify): 要約が空のとき通知を送らないようにする` |
| 起票しない | 「〜を考える」「〜を決める」「〜を検討する」「〜の方針を固める」「〜を調査する」「〜を見直す」 |

- 決めた結果をドキュメントに残すなら、**決めた後に** `docs:` の Issue として起票する。決める作業自体は Issue にしない
- 調査が前提になる項目も、調査だけでは状態が変わらないため起票しない。調査の結果が差分になる形まで決着させてから起票する

## 起票しない項目の扱い

起票できない項目は捨てずに、表の下に「先に決着が必要な論点」として挙げ、
ブレインストーミングを促す。全項目が起票できない場合は表を出さず、この案内だけを出す。

```markdown
先に決着が必要な論点（Issue にしない）:

- （論点）— 何が決まっていないかを 1 文

`/spira:brainstorming <テーマ>` で決着させてから起票します。
```

- 論点は 1 項目 1 行、決まっていないことを 1 文で書く
- 決着のさせ方をここで提案しない。議論は brainstorming の仕事
- ユーザーが「それも Issue にして」と求めても、決着していない項目は起票しない。
  決着した内容を受け取ってから表を作り直す

## 雛形

以下のコードブロックの中身をそのまま雛形として使う。

```markdown
| # | タイトル | 目的 | 完了条件 | 依存 |
|:--|:--|:--|:--|:--|
| 1 | `<type>(<scope>): <説明>` | （課題を 1 文） | （観測できる事実を 1 文） | — |
| 2 | `<type>(<scope>): <説明>` | （課題を 1 文） | （観測できる事実を 1 文） | 行 1, #57 |
```

## 列

| 列 | 内容 | 上限 |
|:--|:--|--:|
| `#` | 通し番号。着手すべき順に振る | — |
| タイトル | 実際に起票するタイトルそのまま。「タイトルの書式」に従う | 説明部 30 字 |
| 目的 | なぜ必要か。現状の課題を 1 文 | 25 字 |
| 完了条件 | 何が満たされたら終わりか。観測できる事実を 1 文 | 30 字 |
| 依存 | 先に完了していないと着手できない Issue。同じ表の行は `行 N`、既存の Open Issue は `#N`。無ければ `—` | — |

## 依存の書き方

依存は、起票後に GitHub の Blocked by として設定する（create-issue の Phase 4）。本文には書かない。

- 依存は「その Issue が完了しないと着手できない」ものに限る。関連するだけの Issue は依存にしない
- 依存先の行は、依存する行より上に置く（`#` が小さい）。依存先から順に起票し、番号を確定させてから Blocked by を付けるため
- 依存先は同じ表の行に限らない。**既存の Open Issue も**すべて照合し、タイトルだけでなく本文（完了条件）まで読んで判断する
- 既存の Issue は Open のものだけを依存先にする。Closed の Issue は依存にしない
- 依存が循環する（行 1 が行 2 に、行 2 が行 1 に依存する）なら、関心事の切り方がずれているサインなので Issue を分割・統合して表を作り直す
- 依存は親子関係ではない。依存があっても Issue はフラットに並べる

## 既存の Open Issue との関係

既存の Open Issue との照合で、依存列に書けない関係が見つかったら、表の下（先に決着が必要な論点の前）に挙げる。無ければ節ごと省く。

```markdown
既存の Open Issue との関係:

- 逆向きの依存: #57 は行 1 の完了後でないと着手できない（承認されたら #57 に Blocked by を付けます）
- 重複のため起票しない: 「〜」は #42 と同じ関心事
```

- 1 件 1 行。理由は 1 文
- 逆向きの依存は、表の承認と一緒に承認されたものとして扱い、起票後に既存の Issue へ Blocked by を付ける

## タイトルの書式

Conventional Commits スタイルで書く。

```
<type>(<scope>): <説明>
```

| 要素 | 内容 |
|:--|:--|
| `type` | 下表のいずれか。必須 |
| `scope` | 変更対象。特定できるなら付ける（例: `spira`, `tts-notify`, `create-issue`）。無理に付けない |
| 説明 | 何をするかを 30 字以内で。体言止めにせず動詞で終える（例: 「〜を追加する」） |

| type | 用途 |
|:--|:--|
| `feat` | 機能の追加 |
| `fix` | 不具合の修正 |
| `refactor` | 振る舞いを変えない内部の変更 |
| `docs` | ドキュメントのみの変更 |
| `test` | テストのみの追加・修正 |
| `chore` | 上記に当てはまらない雑務（依存更新、設定変更など） |

例:

```
feat(spira): 論点テーブルに状態列を追加する
fix(tts-notify): 要約が空のとき通知を送らないようにする
docs: プラグイン仕様にフックの節を追加する
```

- **`type` を推測で決めない**。振る舞いが変わるなら `feat` か `fix`、変わらないなら `refactor`
- **1 つのタイトルに 2 つの type が要るなら、Issue を分割する**

## 記述ルール

- **表の外に補足を書かない**。承認を求める 1 文だけを表の後に添える
- **タイトルは「タイトルの書式」に従う**。Conventional Commits スタイルから外れたタイトルを出さない
- **略語・造語・比喩を使わない**。用語はコードベースとドキュメントに実在する語から借りる
- **実装方法を書かない**。「何を」の粒度に留める
- **完了条件を書けないタイトルは付けない**。「〜の改善」「〜の見直し」はスコープが決まっていないサイン
- **完了条件は観測できる差分で書く**。「〜が決まっている」で終わる行は「起票の可否」に従って表から外す

## 承認の扱い

承認は**表全体に対して**行う。行を選んで一部だけ起票することはしない。

| ユーザーの応答 | 行動 |
|:--|:--|
| 承認 | 表の**全行**を起票する |
| 修正指示 | 指示を踏まえて**表を作り直し**、再提示する。**承認を得るまで起票しない** |
| 詳細の要求 | 対象の Issue **だけ** [issue-body.md](../../../templates/issue-body.md) に沿った本文案を提示し、再度承認を求める |
| 決着していない項目の追加要求 | 「起票しない項目の扱い」に従って先に決着が必要な論点として挙げ、起票しない |

修正指示には、粒度の調整・分割・統合・行の削除・並べ替え・文言の変更が含まれる。
いずれの場合も部分的に起票せず、表を作り直したうえで改めて承認を得る。

承認前に `gh issue create` を実行しない。
