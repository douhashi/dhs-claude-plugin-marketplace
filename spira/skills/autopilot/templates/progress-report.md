# テンプレート: 進捗レポート

- **書き手**: orchestrator エージェント（毎イテレーションの返答）
- **読み手**: ユーザー（メインセッションがそのまま表示する）
- 状態記号は [state.md](./state.md) の「記号」節に従う

## 書き方のルール

- 構成は **現在のライン → 今回の出来事 → 次 → ループ対象の全体像 → NEXT** の順に固定する
- 見出しは `<記号> 自走開発 #<イテレーション> · <時刻>` の形にする。時刻はレポートを書く時点の `date +'%Y-%m-%d %H:%M'`（ローカル時刻）
- ライン表は常に L1〜L3 の 3 行を出す。空いているラインは `空き`
- 表の中のタイトルは 20 字を超えたら末尾を `…` で切る
- 経過時間は分単位（60 分以上は `1時間20分`）
- ログ・エラーの全文・Issue 本文をそのまま貼らない。読んで要約する
- 最終行は必ず `NEXT: wait|halt|done` の 1 行にする

## 今回の出来事の書き方

前回のレポートから変わったことだけを、**1 出来事 1 ブロック**で書く。変化が無ければ節ごと出さない。

```markdown
<記号> **#<番号> <主題>** — <何が起きたか>
> <サマリー 1 行目>
> <サマリー 2 行目>
> <サマリー 3 行目>
```

- **主題**: その Issue が「何についての話か」を、前提知識なしで分かる言葉で書く。Conventional Commits の `type(scope):` は付けず、タイトルの言い換えでよい
- **何が起きたか**: `マージ（PR #30）`・`L2 で開始`・`取り込み` など、出来事を短く
- **サマリー**: **最大 3 行**。対象 Issue の本文・コメント・PR を読み、**何が、どのように変わったのか（変わるのか）**を書く。1 行 1 文、60 字程度まで
  - 手順名や見出し名（`## 実装内容` など）を並べない。変化の中身を書く
  - 1 行で足りるなら 1 行でよい。3 行を埋めるために薄めない

出来事ごとに、サマリーの材料と書く内容は次のとおり。

| 記号 | 出来事 | 読むもの | サマリーに書くこと |
|:--|:--|:--|:--|
| ✅ | マージ | `## 完了報告`・`## 実装内容`・PR の変更ファイル | 何ができるようになったか／何が直ったか、どこを変えたか |
| ▶️ | ライン開始 | Issue 本文（背景・要求・受け入れ基準） | 今どう困っていて、何をどう変える予定か |
| ⛔ | 人手対応待ち | `*.blocked.md`・`## 人手対応待ち` | どこまで進み、何の値が無くて止まったか |
| ⚠️ | 失敗 | 最後の `## CI 失敗`・ラインのログ（`archive/` に退避済み）の最後の `"type":"result"` 行 | どの段階で何が失敗したか、再試行するか |
| 🆕 | 見つかった Issue | Issue 本文・判定・ロードマップ PR | 何が壊れている／何の要望か、判定とその理由、ロードマップのどこに入れたか |
| 🆘 | エスカレーション | escalated Issue 本文・元 Issue の `## CI 失敗` | 何が通らなかったか、自走を続けるか止めるか |
| 🗺 | ロードマップの整合修正（halt / done のみ） | 整合修正 PR の本文 | どの Issue の状態をどう直したか、なぜずれていたか |

⚠️ / 🆘 は、サマリーの後に事後調査コマンドを 1 行足す。`<ROOT>` はルート、`<SID>` は結果表の `SID`（🆘 は元 Issue の行）。
autopilot と同じ `CLAUDE_CONFIG_DIR` で実行する（worktree の再作成は不要）。

```markdown
> 調べる: `cd <ROOT> && claude --resume <SID>`
```

🗺 は Issue 番号の代わりに `**ロードマップ**` を主題にする（例: `🗺 **ロードマップ** — 現状に合わせて修正（PR #35）`）。

## ループ対象の全体像の書き方

`state.md` の「対象 Issue」表から作る。レポートの末尾（`NEXT:` 行の直前）に**毎回**出す。

```markdown
**ループ対象の全体像**

| 順 | Issue | 状態 | メモ |
|:--|:--|:--|:--|
| 1 | #22 設定画面を追加する | ✅ 完了 | PR #30 |
| 2 | #21 ログイン API を追加する | 🧪 CI（L1） | |
| 3 | #31 ログイン API が 500 を返す | 📝 計画（L3） | 🆕 ループ中に取り込み |
| 4 | #24 通知設定を保存する | 🛠 実装（L2） | |
| 5 | #25 通知を送る | ⏸ 依存待ち | #24 の完了待ち |
| 6 | #27 検索を高速化する | ⏳ 待機 | |
```

- 行は「対象 Issue」表の `順` のとおりに並べる（完了したものも消さない）
- 走行中の行は状態の後ろに `（L1）` のようにライン名を付ける
- `メモ` は 20 字程度まで。無ければ空欄
- ループの対象外（escalated・見送った Issue）は載せない

## 走行中（`wait`）

```markdown
## 🔁 自走開発 #5 · 2026-09-18 14:32

| ライン | Issue | 状態 | 経過 |
|:--|:--|:--|--:|
| L1 | #21 ログイン API を追加する | 🧪 CI | 42 分 |
| L2 | #24 通知設定を保存する | 🛠 実装 | 8 分 |
| L3 | #31 ログイン API が 500 を返す | 📝 計画 | 1 分 |

**全体** ✅ 1 · 🚧 3 · 残り 2 · ⛔ 0 · 🆘 0

**今回の出来事**

✅ **#22 設定画面** — マージ（PR #30）
> 通知と表示の設定を、ユーザーごとに 1 画面で変えられるようになった
> 設定は `settings` テーブルに保存し、未設定の項目は既定値で表示する

🆕 **#31 ログイン API が 500 を返す** — 取り込み
> パスワードに記号を含むユーザーがログインできず、#25 の動作確認も進められない
> システムを壊す不具合と判定し、ロードマップの #24 の直前に追加した（PR #33 をマージ）

▶️ **#31 ログイン API が 500 を返す** — L3 で開始
> 入力値のエスケープ漏れで SQL が壊れているため、クエリをパラメータ化して直す

🆘 **#34 #21 の CI が通らない** — 見送り（継続）
> #21 で追加した E2E テストが 3 回とも時間切れになった
> 失敗は #21 の変更箇所に閉じているため、他の Issue は進められると判定した
> 調べる: `cd /home/u/app && claude --resume 3f2c9a1e-7b4d-4e8a-9c0f-1a2b3c4d5e6f`

**次** ラインの完了を待ちます（最長 30 分）

**ループ対象の全体像**

（「ループ対象の全体像の書き方」の表）

NEXT: wait
```

- `全体` の 🚧 は走行中のライン数、`残り` は対象 Issue のうち走行中でも完了でもないもの
- 空きラインがあるのに起動しなかった場合は、`次` の行に理由を 1 文で添える（例: `#25 は #24 の完了待ち`）

## 人手待ちで停止（`halt`）

走行中のラインがすべて終わり、未解消のブロッカーか `停止理由` があるときに出す。

```markdown
## ⏸ 自走開発を止めました #9 · 2026-09-18 17:05

**全体** ✅ 6 · 残り 3 · ⛔ 1

**今回の出来事**

（「今回の出来事の書き方」に従う）

（ここに [blocker-guide.md](./blocker-guide.md) の「環境変数の設定」節か「エスカレーション」節を、orchestrator 用の再開方法で続ける）

**ループ対象の全体像**

（「ループ対象の全体像の書き方」の表）

NEXT: halt
```

## 終了（`done`）

走行中のラインが無く、`spira:pick` が着手できる Issue を返さないときに出す。

```markdown
## 🏁 自走開発が終わりました #12 · 2026-09-18 19:48

**全体** ✅ 8 · ⚠️ 1 · ⛔ 0 · 🆘 1

**今回の出来事**

（「今回の出来事の書き方」に従う）

🗺 **ロードマップ** — ループの結果に合わせて修正（PR #41）
> マージ済みの #22・#24・#31 を `[x]` にし、完了節へ移した
> 失敗して未着手に戻った #27 の `[~]` を `[ ]` にした

**ループ対象の全体像**

（「ループ対象の全体像の書き方」の表。完了していない行は、メモに残った理由を書く）

NEXT: done
```
