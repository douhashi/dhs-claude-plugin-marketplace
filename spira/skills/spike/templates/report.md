# テンプレート: スパイクの報告と提案

- **書き手**: spike スキル（Phase 1 で問いを、Phase 8 で報告と提案を、Phase 9 で PR へのコメントを書く）
- **用途**: 仮実装の結果を伝え、本実装の進め方をユーザーに選んでもらう
- **読み手**: スパイクを頼んだユーザー。PR を開かずに、結果と次の一手を掴みたい

## 問いの提示（Phase 1）

```markdown
## スパイクの問い

| # | 問い | 成功基準 |
|--:|:--|:--|
| 1 | <問い> | <成功基準> |

- やらないこと: <問いに関係しない作り込み>

この問いで仮実装を始めます。
```

## 判断の基準（Phase 8）

上から順に当てはめ、最初に当てはまった進め方を推奨にする。

| 進め方 | 条件 |
|:--|:--|
| `見送り` | 主な問いが `実現不可`、または実現に要る作業がテーマの価値に見合わない |
| `作り直し` | 次のいずれかに当てはまる。近道が本実装の構造に関わる（場所・境界・データの持ち方を変える必要がある）／問いを優先して既存の規約・設計から外れた／本実装が 1 つの PR に収まらず、Issue を分ける必要がある／主な問いに `未確認` が残る |
| `採用` | すべての問いが `実現可` か `条件付きで実現可` で、残る作業（テストの補強・近道の解消・ドキュメントの更新）が同じ PR に足して収まる |

- 推奨の理由は、作業メモの事実（答え・近道・課題）から 1 文で書く
- 好みや一般論で選ばない

## 報告と提案（Phase 8）

上限は **1,200 字**。PR 本文の再掲はしない。

```markdown
## スパイク結果

PR: <ドラフト PR の URL>（PR を作っていなければ「なし（調査で確定）」）

| # | 問い | 答え | 根拠 |
|--:|:--|:--|:--|
| 1 | <問い> | `実現可` | <確かめたことを 1 文> |

- **発見**: <最も大事な発見を 1 文。複数あれば最大 3 つ>
- **課題**: <本実装で解く必要があることを 1 文。最大 3 つ>

## 本実装の進め方

**推奨: <採用 / 作り直し / 見送り>** — <理由を 1 文>

<推奨の進め方の「承認後に行うこと」>

ほかの選択肢:

- <残りの進め方>: <承認後に行うことを 1 文>

どれで進めますか。
```

### 承認後に行うこと

| 進め方 | 書くこと |
|:--|:--|
| `採用` | PR を本実装の書式に書き換え、`spike` ラベルを外してドラフトを解除する。足りない作業（「採用に足りない作業」）を PR にコメントする。マージはしない |
| `作り直し` | `spira:create-issue` で本実装の Issue を起票する（Issue の粒度の見込みを 1 文で添える）。起票後に PR を閉じ、ブランチとワークツリーを削除する |
| `見送り` | 理由を PR にコメントして閉じ、ブランチとワークツリーを削除する |

## 採用に足りない作業（Phase 9）

`採用` で PR に付けるコメント。上限は **500 字**。

```markdown
## 本実装に足りない作業

- [ ] <近道の解消・テストの補強・ドキュメントの更新を 1 項目 1 文>
```

足りない作業が無ければ `本実装に足りない作業はありません。` の 1 行にする。

## PR を閉じるときのコメント（Phase 9）

`作り直し` / `見送り` で PR に付けるコメント。上限は **300 字**。

```markdown
## スパイクの判断

<作り直し / 見送り>: <理由を 1 文>

本実装: #<起票した Issue 番号>（見送りなら行ごと省く）
```

## 記述ルール

- 作業メモにあることだけを書く。`未確認` を `実現可` のように書かない
- 用語はコードとドキュメントにある名前を使う。独自の略語・造語・比喩を使わない
- 経緯（何をどの順で試したか）は書かない。打ち切った問いの障害だけを課題に書く
