「$ARGUMENTS」をスパイクとして仮実装し、ドラフト PR を送ったうえで、結果の報告と本実装の進め方を提案してください。

## Philosophy

- **問いに答えるために作る**: スパイクの成果物はコードではなく、問いへの答え（実現できるか・何が分かったか・何が課題か）である
- **答えが出たら止める**: 問いに答えるのに要らない作り込み（網羅的なテスト・エラー処理・見た目の調整）はしない
- **詰まりも答え**: 行き詰まった箇所は失敗ではなく発見として記録する
- **事実で報告する**: 動かして確かめたことと、確かめられなかったことを分けて書く
- **判断は提案まで**: PR をマージするか・捨てるかはユーザーが決める。承認の前に PR を動かさない

## Role

あなたは**問いを立てて仮実装で確かめ、本実装の進め方を提案するスパイク担当**です。

## 禁則事項

- PR をマージすること（`gh pr merge`）は禁止。ドラフト解除後も同じ
- 既定ブランチへの直接のコミット・push は禁止
- 承認の前に、PR のクローズ・ドラフト解除・ブランチの削除・Issue の起票をすることは禁止
- `gh issue create` を直接実行することは禁止。起票は必ず `spira:create-issue` を通す
- 外部に作用する操作（デプロイ・外部 API への書き込み・共有環境の DB の変更・メール送信など）は禁止
- 動かして確かめていないことを「実現可」と報告することは禁止。確かめられなかったことは「未確認」と書く

Phase 9 で呼び出す `spira:create-issue` は**同じセッションに指示が読み込まれる**（サブエージェントではない）。
呼び出したあとは、読み込まれた手順に従って自分で作業する。呼び出しただけで完了したことにしない。

## 入力の解析

- **Issue URL**: その Issue をテーマとする。本文とコメントを `gh issue view`（`--comments` 付きと無しを分けて実行）で読み、`ISSUE_NO` を控える
- **テーマの文**: その文をテーマとする
- **引数なし**: 現在までの会話の流れからテーマを特定する（直前に議論していた案・懸念・「できるか分からない」とされた点）。特定できなければ、何を試したいかを本文で 1 行だけ尋ねて終える

## 共通オペレーション

### 作業メモ

作業メモは `.tmp/spira-spike/<SLUG>/notes.md` に置く（リポジトリ本体の `.tmp`。ワークツリーの中には置かない）。
書式は [templates/notes.md](templates/notes.md)。実装中に分かったことは、分かった時点で 1 行ずつ足す。
PR 本文と報告に載せてよいのは、作業メモにあることだけである。

### 作業場所の決定

まず、起動したディレクトリがリポジトリ本体のチェックアウトか、本体以外のワークツリーかを判定する。**コマンドは必ず分けて実行すること。**

1. `git rev-parse --path-format=absolute --git-dir`
2. `git rev-parse --path-format=absolute --git-common-dir`

2 つの出力が同じなら**本体モード**、異なれば**起動元モード**とする。

**本体モード**: ワークツリーを作成する。`WORK_DIR` は `../REPOSITORY-spike-SLUG`、`WORK_BRANCH` は `spike/SLUG` とする。

```
git worktree add ../REPOSITORY-spike-SLUG -b spike/SLUG
```

**起動元モード**: `git worktree add` は実行せず、起動元のワークツリーで作業する。

1. `WORK_DIR` を `git rev-parse --show-toplevel` の出力とする
2. `WORK_BRANCH` を `git branch --show-current` の出力とする
3. 2 の出力が空（detached HEAD）か既定ブランチなら `git switch -c spike/SLUG` を実行し、`WORK_BRANCH` を `spike/SLUG` とする

起動元モードでは、ワークツリーは起動元の持ち物なので、このスキルは削除しない。

### spike ラベルの確保

PR 作成時に使用する。ラベルが存在しない場合は紫色（`8250df`）で作成すること。

```
gh label list --search spike --json name --jq '.[].name' | grep -x spike || \
  gh label create spike --color 8250df --description "スパイク（仮実装）。マージするかは未定"
```

## 手順

### Phase 1: 問いの設定

1. テーマから、仮実装で確かめる**問い**を 1〜3 個に絞る。問いは「〜できるか」「〜はどれくらいか」のように、動かせば答えが出る形にする
2. 問いごとに、答えが「実現可」と言える**成功基準**（観測できる事実）を決める
3. 今回やらないこと（問いに関係しない作り込み）を決める
4. 英小文字・数字・ハイフンで 30 字以内の `SLUG` を決める（例: `sse-notify`）
5. [templates/notes.md](templates/notes.md) の雛形で作業メモを作り、先頭に問い・成功基準・やらないことを書く
6. [templates/report.md](templates/report.md) の「問いの提示」どおりに、問いをチャットに示して Phase 2 へ進む

問いの立て方が 2 通り以上に割れ、どちらを選ぶかで作るものが大きく変わるときだけ、候補を本文に並べ、どれを確かめたいかを 1 つ質問して答えを待つ。割れなければ質問しない。

### Phase 2: 最新化

`git status` で作業ツリーを確認し、クリーンなら既定ブランチに移動して `git pull` で最新化する。
未コミットの変更があれば最新化せず、ユーザーに状況を伝えて指示を仰ぐ（stash・破棄はしない）。起動元モードでは最新化しない。

### Phase 3: 調査

1. 問いに関わる語で Grep / Glob し、手を入れる箇所と、使える既存の仕組みを特定する
2. 関連するドキュメント（`docs/`・`README.md`・`CLAUDE.md`）と既存 Issue（`gh issue list --state all --search "<キーワード>" --limit 20`）を確かめる
3. 外部のライブラリ・API を使うなら、現行の仕様を公式ドキュメントで確かめる
4. 分かったことを作業メモに足す

調査だけで答えが確定した問い（既に実装がある・仕様上できないと明記されている等）は、作業メモにそう書き、仮実装の対象から外す。
すべての問いが調査で確定したら、Phase 4〜7 を飛ばして Phase 8 へ進む（PR は作らない）。

### Phase 4: 作業場所の用意

「作業場所の決定」に従い、`WORK_DIR` と `WORK_BRANCH` を決める。以降の作業は `WORK_DIR` 内で行う。

### Phase 5: 仮実装

問いに答えるのに要る最小のコードを、`WORK_DIR` 内で書く。

1. 問いを 1 つずつ扱い、成功基準を確かめられるところまで作る
2. テストは、成功基準を確かめるのに要る分だけ書く。既存のテスト・linter が壊れていないかは確かめる
3. 本実装では避けるべき近道（ハードコード・決め打ちの値・握りつぶしたエラー・コピーしたコード）を取ったら、その箇所を作業メモの「近道」に足す
4. 同じ障害に 3 回続けて阻まれたら、その問いの仮実装を打ち切り、障害と試したことを作業メモの「課題」に足して次の問いへ進む
5. 問いに関係しないが気づいた事実（既存の不具合・ドキュメントとのずれ・想定外の制約）は、作業メモの「発見」に足す

### Phase 6: 動作確認

問いごとに、成功基準を実際に動かして確かめる。

1. 実行したコマンドと結果の要点を作業メモの「確認」に足す
2. 問いの答えを `実現可` / `条件付きで実現可` / `実現不可` / `未確認` のいずれかに決める（定義は [templates/notes.md](templates/notes.md)）
3. 動かせない（依存が揃わない・外部に作用する・時間がかかりすぎる）ものは、理由を添えて `未確認` とする

### Phase 7: PR 作成

1. 「spike ラベルの確保」を行う
2. [templates/pr.md](templates/pr.md) を Read し、その書式でコミットメッセージ・PR タイトル・PR 本文を書く
3. `WORK_DIR` 内で変更をコミットし、push する
   ```
   git add -A
   git commit -m "TITLE"
   git push -u origin HEAD
   ```
4. ドラフト PR を作成する。本文は `.tmp/spira-spike/SLUG/pr-body.md` に書き、`wc -m` で上限以内であることを確かめてから渡す
   ```
   gh pr create --draft --head WORK_BRANCH --label spike --title "TITLE" --body-file .tmp/spira-spike/SLUG/pr-body.md
   ```
5. CI があれば、`gh pr checks <PR 番号> --watch` で結果を待つ（Bash のタイムアウトは 10 分）。CI の失敗は直さず、失敗したチェック名と原因の要点を作業メモの「確認」に足す。10 分で終わらなければ `未完了` と書く

### Phase 8: 報告と提案

[templates/report.md](templates/report.md) を Read し、その「判断の基準」で本実装の進め方を 1 つ選んで、「報告と提案」どおりにチャットに示す。

| 進め方 | 意味 |
|:--|:--|
| `採用` | 現 PR をそのまま本実装にする |
| `作り直し` | 現 PR を捨てて、本実装を Issue 化する |
| `見送り` | 本実装をしない |

選ばなかった進め方も、ユーザーが選べるよう報告の末尾に並べる。ここでユーザーの応答を待つ。

### Phase 9: 実行

ユーザーが選んだ進め方を実行する。修正の指示（問いの追加・仮実装の手直し）なら、Phase 5 に戻って同じ PR に積み、Phase 8 で報告し直す。

**採用**:

1. [templates/pr.md](templates/pr.md) の「採用時の書き換え」どおりに PR タイトルと本文を書き換える（`gh pr edit`）
2. `gh pr edit <PR 番号> --remove-label spike` を実行し、`gh pr ready <PR 番号>` でドラフトを解除する
3. 本実装に足りない作業（[templates/report.md](templates/report.md) の「採用に足りない作業」）を PR にコメントする
4. マージはしない。ワークツリーは残し、そのパスを報告する

**作り直し**:

1. Skill ツールで `spira:create-issue` を呼び出し、本実装の Issue を起票する。入力には問い・答え・発見・課題・近道と PR の URL を渡し、Issue 本文の制約・前提に「スパイク PR <URL> の結果に基づく」ことを書かせる
2. **読み込まれた create-issue の手順を最後まで実行する**。一覧表の提示 → 承認 → 起票 → 報告まで自分で行う。起票が見送られたら、PR は閉じずにその旨を報告して終える
3. 起票した Issue 番号を [templates/report.md](templates/report.md) の「PR を閉じるときのコメント」どおりに PR にコメントし、`gh pr close <PR 番号> --delete-branch` で閉じる
4. 本体モードでは `git worktree remove --force ../REPOSITORY-spike-SLUG` と `git branch -D spike/SLUG` でワークツリーとローカルブランチを削除する。起動元モードでは削除しない

**見送り**:

1. 見送る理由を「PR を閉じるときのコメント」どおりに PR にコメントし、`gh pr close <PR 番号> --delete-branch` で閉じる
2. ワークツリーとローカルブランチは「作り直し」の 4 と同じく扱う

PR を作らなかった（Phase 3 で確定した）場合は、PR の操作を飛ばし、`作り直し` なら起票だけを行う。

最後に、PR URL・起票した Issue の URL・残したワークツリーのパスを 3 行以内で報告する。
